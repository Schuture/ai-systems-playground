# Builder contract: how to add a lab or a teaser to the AI Systems Playground prototype

Read this whole file, then `LAB_UX_GUIDE.md` (same folder) in full, before writing code. The guide is the product owner's review rules; violating them is a bug even if the code works.

## 1. What the prototype is

- One self-contained HTML page (published as a claude.ai artifact) built from sources in this folder:
  - `python3 build.py` concatenates `head.html`, `styles.css`, `labs/*.css`, `teasers/*.css`, `body.html`, and the scripts `app.js`, `labs/*.js`, `teasers/*.js`, `main.js` into `ai-systems-playground.html`.
- `app.js` holds the core, the home page (system map + lab tiles), and the KV cache lab (`#kv-cache`), which is the reference for quality and tone. Open the built page and go through the KV lab once in both languages before you start.
- Your code goes only into your own files: `labs/<id>.js` (+ optional `labs/<id>.css`) or `teasers/<name>.js` (+ `.css`), and tests under `tests/`. **Do not edit** `app.js`, `styles.css`, `body.html`, `head.html`, `build.py`, `main.js`. If the kit is missing something, implement it locally in your module and list it in your report.
- Plain JavaScript, no libraries, no network requests, no `localStorage` for lab state. Wrap your file in an IIFE with `'use strict'`.
- Languages: English is the source text, Chinese follows. Every visible string exists in both, via `A.tx(en, zh)` or `A.L({en, zh})`. Technical terms stay in English inside Chinese sentences (KV cache, batch, prefill, token, DPO, β, logit …). No uppercase in Chinese text.

## 2. The kit: `window.ASP` (use `const A = window.ASP`)

Text and numbers
- `A.lang()` → `'en'|'zh'`; `A.tx(en, zh)`; `A.L({en, zh})`; `A.t(key)` for shared strings (`modeGuided`, `modeSandbox`, `modeChallenge`, `share`, `crumbMap`, `showMath`, `ctrlEyebrow`, `reset`, `cMin`, `cProd`, `cPapers`, `connEyebrow`, `connTitle`, `copyCode` …).
- `A.addStrings({en:{…}, zh:{…}})` registers keys for `data-tip="key"` tooltips. Prefix your keys with your lab prefix (`pa_…`).
- `A.fmt.B(bytes)` (e.g. "5 GiB"), `A.fmt.num(v, digits)`, `A.fmt.int(n)` (thousands separators), `A.fmt.tok(tokens)` ("128K"), `A.fmt.users(n)`, `A.fmt.gpus(n)`, `A.fmt.mins(n)`; constants `A.KiB/MiB/GiB/TiB`.
- `A.esc(s)`, `A.$(sel, root)`, `A.$$(sel, root)`, `A.reduceMotion()`.

UI builders (return HTML strings; insert, then call `A.ui.initRanges(container)` for sliders)
- `A.ui.range({id, key, label, min, max, step, value, out, note, inline})` → a slider. The input gets `id="${id}-in"` and `data-key=key`. `inline:true` renders the dashed "control inside a step card" style; otherwise the Controls-panel style. The filled part of the track follows the value however it changes: the reader's drag or keys, `input.value = …` or `input.valueAsNumber = …` in code, a new `min`, `max`, `step` or `value` attribute, a slider added to the page without `A.ui.initRanges` (kit polish K5). `A.ui.setRange(input)` still repaints it but is no longer needed.
- `A.ui.seg({id, key, label, options:[[value, text, disabled?]], value, note, inline})` → segmented buttons (`button[data-v]` inside `.seg-ctl[data-key]`). Update with `A.ui.setPressed(segEl, value)`.
- `A.ui.levers({aria, value, options:[{v, title, desc, result}]})` → single-choice options with radio dots (`button[data-lever]`). The result slot `.lv-r` sits on the title row, right-aligned, while the title fits on one line beside it; when it does not, the result drops under the title (still right-aligned) and the title keeps the row's whole width, so a narrow rail never squeezes it into a thin column. The description spans the full width below (guide R3.6, R3.10). An empty result takes no room. Use for "try one of these" steps; after a click, bring the result box into view if its top is below the fold.
- `A.ui.cmpChart({title, aria, rows:[{label, value, text, ok, me, best, tags:[{text, me}]}], goal, goalLabel, max, brief, briefMax, hiddenText})` → horizontal comparison bars with an optional dashed goal line (guide §5). With `brief:true` (every challenge result, guide R4.6) it keeps only the rows that meet the goal (`ok`), the pick (`me`) and the tagged rows (the initial setup), in the given order, and writes under the chart “The other N options miss the goal and are not shown.” / “其余 N 种没达到目标，图里没有列出。” (`hiddenText:n=>…` words it differently, e.g. “其余 N 种放不下。”). When more than `briefMax` (8) rows would stay and some rows carry `best:true` (from the engine), the chart shows the pick, the tagged rows and the best rows, and every passing row goes behind a closed “See all settings that pass (N)” / “看全部可行的设置（N 种）” (`details.cmp-more`). Test: `tests/kit_brief_chart.py`. A passing row (`ok:true`) is green and its track has a green ring, so it shows at any value, 0% included; the legend's swatch shows the same. Value labels stay on one line and in their own row, and no reference line (the dashed goal or budget line) ever runs through one: the kit measures each label and puts it in the first of these places that keeps 4 px from every line and stays in the track: right of the bar's end; inside the bar's end; the place nearest the bar's end just past or just before a line (beside the bar or inside it, never across its end); else under the bar's end, the row growing to hold it (kit polish K1; app.js `cmpPlaceAll`, styles.css 1c `--cx`, `.cmp-lo`). It measures when the chart is added, when a track or a label changes size (a resize, a language switch, “See all settings that pass” opened) and when a late font arrives. A lab's own chart gets the same placement from the same markup: `<div class="cmp-track cmp-cq">…<b class="g" style="left:G%"></b><span class="cmp-val cmp-fit" style="left:P%;--v:P">…</span></div>` (as mha's challenge chart does). Do not move value labels yourself, put a background under them to cover a line, or add an “inside the bar past N%” rule of your own; a label a lab places itself (an inline `right`, no `.cmp-fit`, or a lab rule that moves it) is left where the lab puts it. The goal label is centred on the goal line and kept inside the chart near either end.
- `A.ui.steps({steps:[{title}], current, body, back, showMe, next, nextDisabled, nextWhy, skip})` → the guided rail. The current step contains an empty `.obs[data-obs]` box (hidden) that you fill and unhide; buttons carry `data-go=i` and `data-nav="back|showme|next|skip"`. `nextWhy` (optional, a short HTML sentence, e.g. "Pick an answer to continue, or Skip.") says why Next is disabled: a line `p.nx-why[data-next-why]` under the card's buttons and, with `m2`, under the phone part bar's buttons. It shows while Next is disabled; when Next is enabled (in place, `b.disabled=false`, or by a re-render) it goes blank but keeps its height, so nothing below it moves. Pass it for every part whose Next can be disabled. `A.ui.setNext(root, disabled, why?)` sets every Next in `root` (card and bar) and, if given, the line's text.
- `A.ui.status(ok, text)`, `A.ui.flash(el)`, `A.ui.jumpToEl(el)` (open enclosing `<details>`, scroll to center, focus, highlight), `A.ui.obsBump(box)` (blink a result box after a click changed it).

Lab shell
- `A.shell.header({id, world, short, title, minutes, level, fid, fidPop, primer, primerPop, descs:{guided, sandbox, challenge}, mode})` → breadcrumb, question title, tags, fidelity and primer popovers, the three mode buttons (hover shows `descs`), the always-visible mode description, and the share button. `fid` ∈ `Analytical|Simulated|Replay|Live|Conceptual`; the header shows the home-tile words for them: Analytical → 公式计算 / Formula, Simulated and Live → 玩具实跑 / Toy run, Conceptual → 示意 / Illustrative. `level` is accepted but no longer shown.
- `A.shell.bindHeader(root, {id, onMode(m), token()})` wires popovers, mode buttons and "copy setup link" (`#<id>~<token()>`).
- `A.shell.setMode(root, m, descs)` updates pressed state and the description.

Tooltips and jumps (no code needed besides attributes and the lab hooks below)
- `data-tip="key"` shows `A.t(key)`; `data-tipx="…"` shows that literal, already localized text. The kit makes every such trigger reachable by keyboard (see §14): an element that is not a native control gets `tabindex="0"` (and, without text, an `aria-label` with its tip); focus shows the tip, blur and Escape hide it. Keep tip triggers out of `aria-hidden` boxes, or they stay mouse-only.
- Add `data-jump="key"` to make the element clickable; the tooltip gets an action line from your `jumpAct(key)`, and a click calls your `jump(key, el)`.
- Formula terms: `<span class="t" tabindex="0" role="button" data-ctl="key">…</span>` → tooltip from your `termTip(key)`, click and Enter call `jump(key, el)`.
- `A.tip.show(el, html)` / `A.tip.hide()` for anything else (for example "fixed during the challenge" feedback on a click). `A.tip.quiet()` hides the tooltip and keeps it away until the pointer really moves: call it from a button pressed again and again under a resting pointer (▸ / ◂), so its tooltip does not cover what the press changes.

Registration
```js
A.registerLab({
  id: 'paged-attention',                 // must equal the catalog id
  mount(root, token) {},                  // render the whole view into root (it is empty), bind listeners on root; state lives in module scope
  leave() {},                             // stop timers / animation frames; drop references to root
  onLang() {},                            // re-render text (re-mounting is fine; keep state)
  onResize() {},                          // optional
  termTip(key, el) { return '<div>…</div><div class="act">…</div>'; },
  jump(key, el) {},                       // scroll to and highlight the control, or explain why it is fixed
  jumpAct(key) { return '…'; },           // e.g. "Click to jump to “Block size”."
  snap() { return {v:1, mode, step, S:{...S}, pred, /* … */ passed}; },   // the learner's state, JSON-safe (section 16)
  restore(o) {},                          // put a snap() back into the module variables before the first mount; validate, never render
  dock: {                                 // mini result bar under the top bar when the main visual scrolls away
    anchor() { return mainVisualEl; }, bench() { return benchEl; }, target() { return stageGraphEl; },
    render({status, vis, read}) {}        // status: set className 'status ok|bad' + short text; vis: a small visual; read: one full sentence
  }
});
A.registerTeaser('paged-attention', { render(el) {} });   // el = the tile's teaser area; rebuild fully, keep state in module scope
```
- A teaser registered with `placeholder: true` (the set C tiles for labs not built yet) yields to the lab's own teaser, whichever file loads first; a lab's own teaser never sets it.
- `A.hash.write(token)` after every state change (the URL becomes `#<id>~<token>`; `mount` receives it back). Tokens use only letters, digits, `.`, `-`, `_`.
- `A.dock.refresh()` after every render. `A.announce(text)` for a short screen-reader summary after changes.
- `A.catalog` gives `{LABS, LAB, WORLDS, PATHS, labStatus}`; `A.kv` exposes the KV lab engine (`compute`, `MODELS`, `GPUS`, `PREC`, `DEFAULT`, `perGpuBar`, `drawBar`, `drawAxis`) if you want to reuse the memory model.

A complete, working, deliberately small example that uses every hook is in `specs/example-lab.js` (copy it to `labs/` and open `#_example` to try it; do not ship it). Its copy text is minimal on purpose; write yours by the guide.

## 3. Conventions

- Every id and every custom CSS class starts with your prefix (`pa-`, `cb-`, `dpo-`, `tz-<name>-`). The KV lab's ids (`#rail`, `#stage`, `#controls`, `#modeDesc`, `#math` …) are taken.
- Listeners go on your `root` (or on elements inside a teaser's `el`), never on `document`/`window` (the core already handles tooltips, jumps, scroll and resize).
- Layout: reuse the KV lab's structure and classes: `.wrap.bench` containing `aside.rail`, `div.panel.stage` (sticky, contains `.stage-head`, `.legend-row`, `.stage-graph.graph`, `.metrics`, `details.math`), `aside.panel.controls`; then `section.wrap.connect` with `.connect-grid` of `.c-card`s. Useful classes: `.railcard .rh .obs .choices .choice .levers .inline-ctl .goal .progress .presets .preset .ctl .ctl-note .ctl-hint .ctl-lock .seg-ctl .metric .status .tag .btn .btn.ghost .btn.sm .linkbtn .eyebrow .small .muted .mono .okline .badline .cmp .code .refs`.
- Colors: tokens only (`var(--ink)`, `--ink-2`, `--ink-3`, `--line`, `--line-2`, `--surface`, `--surface-2`, `--sunken`, `--bg`). Data colors: weights `--c-weights` (blue), KV cache `--c-kv` (amber), runtime overhead `--c-overhead` (violet). `--c-oom` (red) only for failure, `--c-ok` (green) only for success. Everything else grayscale. Must look right in dark mode too (tokens handle it; test it).
- While the user drags a slider, never re-render the element containing it; update text and visuals in place.
- Animations: `requestAnimationFrame`, stop in `leave()`, respect `A.reduceMotion()` (jump to the end state instead).
- Numbers shown on the page come from your pure `compute()`/simulation functions, never typed into the copy by hand. Simulations are seeded and deterministic.

## 4. What a lab must contain (match the KV lab)

0. **Before any copy, write the reader model in your spec**: what the reader already knows (which earlier lab), the one new idea this lab teaches, and the problem it solves. Every card teaches one new thing in at most 3 short paragraphs; side facts go to the Fidelity popover. Then write by LAB_UX_GUIDE R6.13–R6.17: every number says what it counts, where, and whose; no "·" joining clauses; tooltips are full sentences with a subject; no instructions the interaction already shows; no quotes that do not directly help; "初始设置 / initial setup" for the baseline; "room for N tokens" instead of "slots". Export the whole text in reading order (see `tests/pa_copy_deck.py`) and read it before you report.

1. Header via `A.shell.header`, with a fidelity popover that says what is modeled, what is simplified, and the sources, and states every estimate as an estimate (guide R2.7).
2. Guided mode, 5–8 steps: Mission (concrete setup with real model / hardware names), Predict (multiple choice, locked in), several Explore steps each with the one control it asks for inline in the card and an observation that states the result with its baseline, an Explain step with the key formula, and "What to remember" with 2–3 misconceptions checked and a button into the challenge.
3. Free-explore mode: 3–6 real-world presets as single-choice buttons whose pressed state follows the settings, plus every control in the Controls panel.
4. Challenge: a goal written in full (model, hardware, condition, target number, guide R6.8), only the allowed controls inside the task card, the rest hidden with a note, live progress, "Submit my answer" with three-tier feedback (met and minimal / met but a smaller change exists / not met with a hint and a "Show the answer" / “直接看答案” link), a brief `cmpChart` (`brief:true`: the passing settings, the initial setup and "your pick", never every option; guide R4.6), then baseline → effect → reason text and a specific caveat. Check it with `python3 tests/chal_result_check.py <lab>`.
5. Stage: one main visual that makes the mechanism visible, a legend whose items have tooltips, 3–5 metric cards with tooltips and ▲▼ deltas, "Show the math" with `.t` terms wired to controls.
6. Controls panel: a one-line hint on where to look, every control labeled in plain words, every assumed parameter with a note under it saying what it is, why it is assumed, what it depends on, its usual size and why (R2.7).
7. Mini result bar (`dock`) for narrow screens.
8. Connect section: a minimal implementation (≤ 40 lines), "In production" pointing at the real code (file path in vLLM / SGLang / TRL; no fake line numbers), 2–3 papers with links, and an interview-style question generated from your engine with a worked answer.
9. The teaser for the home tile (see §5).
10. Bilingual, keyboard-reachable, reduced-motion safe, no horizontal scroll at 390 px.

## 5. What a teaser must contain (updated in round 5)

- One control (slider, segmented buttons or a single-choice lever), one small visual (≤ 130 px tall, inline SVG or bars built from divs), and **one sentence in `.tz-read` of at most 25 English words** (Chinese about as short) that restates the condition and the result and changes on every interaction. No second sentence, no "Try the idea…", no status text: the tile shows the status.
- **Everything else goes into `.tz-note` elements**: assumptions, sources, "illustrative, not a recording", formulas, what the numbers leave out. On the home page `.tz-note` is hidden and not shown anywhere on the tile (owner 2026-10-13: the tile is one button, no "Assumptions & sources" on it; the lab page's end notes carry the same facts). Keep notes plain text: no links, no buttons, no nested `data-tipx` (merge that text into the note). You may keep updating a note's text as the state changes.
- **If the visual uses colour or hatching, add a one-line legend** `<div class="tz-leg">` with items `<span><i class="sw …"></i>word</span>` (kit swatches: `sw w`, `sw kv`, `sw oh`, `sw free`, `sw res`, `sw over`; or your own `<i>` with a background). Items may carry `data-tipx`.
- Colours follow R5.6: blue = weights, amber = KV cache, violet = runtime overhead, red = failure, green = success. Anything else (chosen vs rejected, requests, slots, tokens) is grayscale: `--ink`, `--ink-2`, `--ink-3`, hatching.
- Animations and replays have a speed control (slow / medium / fast, time-based), a pause, a single step and a scrubber (R3.9).
- Units: tokens use K = 1,024 ("32K" = 32,768); write decimal counts in full ("10,000-token"). Memory in GiB; if a vendor figure is in GB, say both ("80 GB = 74.5 GiB") or say that it is read as GiB.
- The tile shows a chip for how the teaser's numbers are made — Formula / Toy run / Illustrative — set by the core from the lab id; your `.tz-note` must agree with it (e.g. an illustrative teaser says so in its note).
- Base classes: `.tz` (grid), `.tz-lab` (label + `<output>`), `.tz-vis`, `.tz-read`, `.tz-leg`, `.tz-note`; segmented buttons via `A.ui.seg({… inline:false})` render fine inside tiles. Everything else prefixed `tz-<name>-`.
- Tile width is 280–440 px. It must be readable at 280 px and in dark mode.
- The idea must be correct and self-contained: a formula or a small seeded simulation you verified in Python. No claims you cannot back with a source or with the formula shown. Numbers on the tile must match the lab's own assumptions (same workload rule, same pool, same step-time model) or the note must say why they differ.

## 6. Tests you must write and run

- Several builders work in this folder at the same time. **Never build to `ai-systems-playground.html`**, and never wrap into `wrapped.html`. Build your own page with only your files: `python3 build.py out/<id>.html --only <your file stems>` (e.g. `--only paged-attention` for `labs/paged-attention.js` + `.css`; teasers by their file stem). Wrap it into `out/wrapped-<id>.html` in your tests.
- Name your teaser files `teasers/<lab-id>.js` (one file may register several teasers; then name it after your set, e.g. `teasers/set-a.js`).

- `tests/<id>_numbers.py`: recompute every key number your page shows, independently in Python (do not port your JS line by line; derive it), assert equality with the page by evaluating your JS engine through Playwright (`page.evaluate`) or by exposing a read-only hook `window.__<prefix>` from your module.
- `tests/<id>_flow.py`: Playwright (Chromium is preinstalled; wrap the page in a doctype skeleton like `tests/kit_example.py` does). Walk every mode and every step at 1440×900 and 390×844 in EN and ZH; check no page errors, no horizontal overflow, the next-step gating, the challenge feedback tiers, the language switch keeping state, the hash round-trip, and the dock at 390. Save screenshots to `shots/<id>/` and look at them yourself.
- The existing checks must keep passing: `python3 check4.py`, `python3 check7.py` (KV lab), `python3 tests/kit_example.py` (after temporarily copying the example in, if you want). Console errors about fonts (`ERR_TUNNEL`) are expected in this sandbox and can be ignored.
- While you fix things, run only the part of your flow test that your change touches (filter by part, width or language), then run the full suite once when all fixes are in; at most two full flow runs per fix round (LAB_UX_GUIDE R0.4). The machine has 2 CPUs: run your tests one at a time.

## 7. Your report (final message)

- Files you created.
- The learning design in 10 lines: mission, prediction, steps, challenge, what the visual shows.
- Every number the page states, with how you verified it.
- Every factual claim with its source URL.
- Guide rules you could not meet, and why; gaps in the kit you worked around.

## 8. Round 5 kit additions and rules (read before fixing review findings)

New kit helpers (in `app.js`, available as `window.ASP`):
- `A.ui.reveal(el)`: if `el`'s top edge is off screen (or hidden under the top bar / mini result bar), scroll it just below them. On phones (≤ 760 px) it always brings the new card to that top edge: under the mini result bar when the bar will show once the page has scrolled there (the card's control and the bar then share the screen), else right under the top bar. It keeps no room for a bar that will not come (kit polish K3). One case K3 misses (kit polish r2): on a phone whose title ends 14–64 px above the bench (the outcome and the minutes tag on two lines), Scenarios or the Challenge lands the bench under the room kept for the bar, but the bar stays hidden because the title's last pixels are still below the top bar; the room shows the end of the header and nothing is covered. After a click that changes the part or the mode it still goes to the part bar or the stage (R3.7). The mini result bar stays hidden until the lab’s title has scrolled under the top bar, at every width (see §9). **Call it after every user-triggered Next, Back, step-header click, "Take the challenge", and mode switch**, with the new step card (or the rail) as `el`. Do not call it on the initial mount.
- `A.fmt.delta(a, b, {pts, dp, base})`: a metric change that states its baseline (unless `base:false`, below), computed from the values as shown (`dp` = the decimals the card shows; both values are rounded to it first). Formats: "▲ 41 pts vs last" / "▲ 41 个百分点（比上次）" (`pts:true`); "▲ 2.1 times the last value" / "▲ 是上次的 2.1 倍" for 2× or more; every decrease as a percentage, "▼ −26% vs last" / "▼ −26%（比上次）" ("−99.9%" when it would round to −100% but is not 0); "▲ up from 0" / "▲ 上次是 0", "▼ down to 0" / "▼ 降到 0". An empty string means no change: clear the badge. Show a badge only after the learner's own change (a control, an option, a scenario, Show me), never on entering a part, Back/Next, a mode switch, or a state the lab sets (R6.6). `base:false` (kit polish K2) writes the change alone, with no comparison: “▲ 41 pts” / “▲ 41 个百分点”, “▲ 2.1×” / “▲ 2.1 倍”, “▲ +58%”, “▼ −62%”, “▲ up from 0” / “▲ 从 0 升上来”, “▼ down from 0” / “▼ 从 0 降下来”, “▼ down to 0” / “▼ 降到 0”. Use it only where the comparison is named once for the whole group of cards: a line right above the cards that shows with their ▲▼ (“▲▼ compared with “Just-launched chat app”” / “▲▼ 和“刚上线的聊天应用”比”; product-design), or each card's tooltip (“▲▼: the change from the last setting.”; chunk-rerank). Without it the output is unchanged. Do not cut the comparison off a returned string.
- `A.fmt.G(bytes)`: GiB with no switch to TiB, so side-by-side values share one unit.
- `A.ui.cmpChart({…, okText, noText, goalText, legend})`: rows with `ok:true` are now drawn green (success colour) and the chart ends with a legend: "■ meets the goal ■ misses it ┆ goal". Pass `okText` / `noText` when "the goal" needs to be specific (e.g. "meets both targets" / "misses at least one"). `legend:false` hides it.
- `.choices .choice` buttons now show a radio dot automatically (single choice, R2.5).
- Layout at ≤ 760 px is now: rail (step cards) first, then the stage, then controls (R7.3). The mini result bar (`dock`) keeps the result in view while the stage is below. Check your 390 px flow still reads well: nothing in a step card may say "above"/"below" about the stage; say "in the chart" and, if needed, give a link that jumps to it.
- Tooltips no longer pop up after a programmatic scroll, or after a click that re-renders the rail or switches mode, until the pointer really moves (R1.7). If a test hovers an element right after a scroll or click, move the mouse onto it (Playwright `hover` does this).
- Speed controls: "Show me" may play one run fast, but it must not change the learner's speed setting (R3.9).
- Card height: measure each guided card after its action at 1440×1000; the result and the verdict on a prediction come first and must be on screen (R3.10).

Rules added from the round-4 reviews (they apply to every lab; see `LAB_UX_GUIDE.md`):
- A prediction can still be changed until the result is shown, so never write "Locked in". Write "Saved. You can still change it before …" / "已记下，…之前还可以改".
- Do not reveal a prediction's answer anywhere before the learner answers: not in the stage, the metric cards, the status badge, its tooltip, or the mini result bar.
- Nothing may show a finished result before the action that produces it (e.g. a run's totals before Play finishes): show the live clock value, or grey the card and title it "Whole run (all N requests)".
- One term, one meaning, on the whole page (e.g. "margin"). If two quantities are related, give them two names and define both.
- Names (R2.1): the kit calls the modes 分步引导 / 应用场景 / 挑战题 (Guided / Scenarios / Challenge). The scenario rail card is "选一个应用场景" / "Pick a scenario"; the settings panel is "自由调参" / "Settings" (never "控件" / "Controls"). No sentences about the page's own behavior (R3.4), e.g. when the mini result bar appears. The writing pass for every lab is in `specs/copy-pass-v2.md`.
- Guided cards are "part N" / "第 N 部分" in text (the kit's rail reads "3 of 7" / "3 / 7", buttons Back / Next = 上一部分 / 下一部分); keep "step" / "步" for the engine ("decode step", "engine step").
- Every colour or line style in a chart is in its legend (dashed comparison lines too), in dark mode as well as light (say "thick line", not "dark tick").
- Formula lines must reproduce from the numbers shown: put in values with enough digits, and compute differences from the displayed (rounded) values.
- A fixed sentence must not contradict the numbers next to it at edge states (0 steps, the last step, extreme settings): gate it on the state.
